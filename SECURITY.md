# Security Policy

AEWhite Devs takes the security of its software, infrastructure, users, and services seriously.

If you discover a security vulnerability in any AEWhite Devs project, please report it responsibly and privately.

## Reporting a Vulnerability

**Do not open a public GitHub issue for security vulnerabilities.**

Security reports should be sent privately to:

**[security@aewhitedevs.com](mailto:security@aewhitedevs.com)**

Please include as much of the following information as possible:

* A clear description of the vulnerability.
* The affected repository, component, application, or service.
* Steps required to reproduce the issue.
* Expected and actual behavior.
* Potential security impact.
* Relevant screenshots, logs, requests, responses, or proof-of-concept information.
* Any suggested mitigation or fix, if available.

Please avoid including unnecessary personal information or sensitive user data in your report.

## Scope

Security reports may include vulnerabilities affecting:

* AEWhite Devs applications.
* Backend APIs and services.
* Web applications and administrative interfaces.
* Mobile applications.
* Authentication and authorization systems.
* Infrastructure and deployment systems.
* CI/CD pipelines.
* Public APIs and integrations.
* Business and provider platforms.
* Dependencies used by AEWhite Devs software.
* Misconfigurations that may expose protected information or systems.

## Responsible Disclosure

Researchers and contributors are expected to:

* Report vulnerabilities privately.
* Avoid accessing, modifying, deleting, or downloading data that does not belong to them.
* Avoid disrupting production services.
* Avoid denial-of-service testing.
* Avoid social engineering, phishing, or physical attacks.
* Stop testing once enough information has been collected to demonstrate the vulnerability.
* Allow AEWhite Devs reasonable time to investigate and remediate the issue before public disclosure.

## Out of Scope

The following are generally not considered valid security vulnerabilities unless they demonstrate a meaningful security impact:

* Missing security headers without a demonstrated exploit.
* Self-XSS.
* Clickjacking on pages without sensitive functionality.
* Rate-limiting observations without demonstrated abuse.
* Vulnerabilities that require physical access to an already compromised device.
* Reports generated exclusively by automated scanners without validation.
* Denial-of-service or stress testing.
* Social engineering attacks.
* Issues affecting unsupported or obsolete versions of software.
* Publicly documented behavior that does not create a security boundary violation.

## Response Process

After receiving a valid report, AEWhite Devs will attempt to:

1. Acknowledge receipt of the report.
2. Review and validate the reported issue.
3. Determine severity and affected components.
4. Develop and test an appropriate remediation.
5. Deploy the fix where necessary.
6. Coordinate disclosure when appropriate.

Response times may vary depending on severity, complexity, and availability of the affected systems.

## Confidentiality

Security reports and related communications should remain confidential until AEWhite Devs confirms that disclosure is appropriate.

Information about internal infrastructure, credentials, customer data, private source code, or other confidential systems must not be publicly disclosed.

## Supported Versions

Security fixes are generally provided for actively maintained versions of AEWhite Devs software.

Repositories may define their own supported-version policy where necessary.

## Security Updates

Security-related changes may be released without detailed technical information until affected systems have been updated and the risk of exploitation has been reduced.

## Safe Harbor

AEWhite Devs intends to treat good-faith security research conducted according to this policy as authorized activity.

Researchers acting responsibly, avoiding harm, respecting privacy, and following this disclosure process should not be considered malicious solely for reporting a vulnerability.

This safe-harbor statement does not authorize activity that violates applicable law, compromises third-party systems, causes disruption, or exceeds what is reasonably necessary to demonstrate a vulnerability.
